
## 一、设计背景

这套机制面向的是持续推进的知识型项目。

以一个“新产品上市项目”为例，项目可能包含：

- 澄清目标用户和项目范围；

- 收集访谈、市场数据和竞品资料；

- 提炼需求与关键认识；

- 比较定价、渠道和推广方案；

- 作出重要选择；

- 制作上市计划、汇报材料和执行模板；

- 根据反馈持续修订成果。

这类项目通常通过自然对话推进，我们利用AI完成这些工作时，可能会说：

- “目标用户先聚焦中小团队。”

- “渠道 B 暂时不投入。”

- “这份上市计划作为当前版本。”

- “这个结论还需要补充访谈验证。”

- “旧方案可以保留，但不能再作为执行依据。”

这些表达看起来只是对话，实际上可能分别代表：

- 项目范围发生变化；

- 一个方案被暂缓；

- 某份文件成为权威版本；

- 一个结论仍处于待确认状态；

- 旧版本需要进入历史归档。

如果这些信息只停留在聊天里，后续就容易出现上下文丢失、重复讨论、版本不清和项目无法连续推进的问题。

因此，我希望让 AI 不只回答当前问题，还能够承担一部分“项目知识管家”的职责：

> 用户通过自然对话推进思考，AI 负责识别任务、结论、决定、成果和遗留问题，并将它们维护到合适的位置。
> 
> 

## 二、为什么使用了 `AGENTS.md` 和 Skill

两者承担不同层次的职责。

可以把它们理解为：

- `AGENTS.md` 是项目的“本地协作宪法”；

- Skill 是 AI 的“知识项目工作方法”。

### `AGENTS.md`：项目级规则

`AGENTS.md` 回答的是：

> 在这个具体项目中，AI 应该按照什么约定工作？
> 
> 

例如，在这个项目中，它可以规定：

- 有哪些正式目录；

- 当前知识、工作材料和成果分别放在哪里；

- 任务目录采用什么命名格式；

- 每日迭代如何记录；

- 哪些维护操作可以直接进行；

- 哪些重要调整需要用户确认；

- 修改文件后应如何向用户说明。

这些规则与具体项目有关。另一个项目可以采用不同的目录结构、日期格式和权限边界。

### Skill：通用判断机制

Skill 回答的是：

> AI 应该如何从自然对话中识别并维护有长期价值的项目信息？
> 
> 

它主要负责判断：

- 当前是在临时交流，还是已经形成持续任务；

- 用户是在探索，还是已经作出决定；

- 某个结论是否已经稳定；

- 是否需要建立工作记录；

- 什么内容值得进入正式知识；

- 什么内容仍然只能标记为暂定；

- 任务何时已经在收尾阶段；

- 哪些内容应保留，哪些内容没有长期价值。

Skill 不应替所有项目规定同一种目录或命名格式，而是优先遵循项目自己的 `AGENTS.md`。

因此，整体权威顺序是：

```Plain Text
用户当前明确要求
        ↓
项目 AGENTS.md
        ↓
项目已有正式知识
        ↓
通用 Skill
```

## 三、核心设计思路

### 以自然对话作为工作入口

用户不需要主动声明：“这是一个新任务”、“现在应该记录”、“这个阶段应该结束了”、“请调用某个 Skill”等。

AI 会根据对话内容和项目状态，判断当前处于什么阶段。

只有当判断会影响项目方向、正式结论、重要文件或目录结构时，才需要向用户说明或请求确认。

这样可以让项目管理服务于思考，而不是打断思考。

### 按任务目的组织内容

AI首先会识别材料服务于哪个任务目的。

比如，在“新产品上市项目”中，可以形成这些任务：

```Plain Text
目标用户研究
定价策略
发布渠道选择
上市计划
上市效果评估
```

例如：

- 用户访谈、用户特征总结和需求判断属于“目标用户研究”；

- 价格测算、方案比较和定价决定属于“定价策略”；

- 渠道数据、渠道比较和投放计划属于“发布渠道选择”。

这样，同一任务的背景、分析、决定和成果能够保持关联。

### 根据材料当前作用进行分层

确定任务以后，再判断材料在这个任务中当前发挥什么作用。

同一个任务可以同时出现在多个目录中。

例如，“定价策略”可能包含：

```Plain Text
docs/定价策略/          当前采用的定价原则
work/定价策略/          尚未完成的价格验证
outputs/定价策略/       可直接使用的价格方案
references/定价策略/    市场数据和访谈证据
archive/定价策略/       已经放弃的旧定价方案
```

它们不是五个不同任务，而是同一任务的不同材料层次。

### 让内容具有明确生命周期

在真实工作中，我们的思路往往是从探索逐渐走向稳定的。因此，项目文件的组织也应该遵循这样的习惯：

```Plain Text
自然对话
   ↓
持续探索
   ↓
work：形成工作主题
   ↓
确认、验证或收敛
   ├── docs：稳定知识
   ├── outputs：正式成果
   ├── references：来源与证据
   └── archive：旧版本和完成过程
```

例如，我们提出：

> “我们可能应该采用订阅制，但还需要验证客户接受度。”
> 
> 

此时它仍是暂定方案，应进入工作记录。

后来，经过访谈和价格测试，最终确认：

> “正式采用基础版加专业版的订阅方案。”
> 
> 

这时AI就可以：

- 将定价原则沉淀到 `docs/`；

- 将正式价格表放入 `outputs/`；

- 将访谈和测试数据保留在 `references/`；

- 将已经放弃的旧方案放入 `archive/`。

### 一个主题只保留一个当前权威版本

项目允许保留历史版本，但需要明确当前使用哪一个版本。

以“产品上市计划”为例：

- 当前上市计划进入 `outputs/`；

- 当前采用的策略和关键判断进入 `docs/`；

- 市场调研和预算依据进入 `references/`；

- 旧计划和已结束的设计过程进入 `archive/`；

- 每日迭代日志记录当天确认或调整了什么。

其他位置通过摘要和链接关联权威文件，不保存相互竞争的完整副本。

### 同时提供任务视角和时间视角

按任务组织的目录回答：

> 关于“目标用户研究”或“产品上市计划”的内容都在哪里？
> 
> 

`iteration/` 回答：

> 某一天，这个项目具体推进了什么？
> 
> 

因此，项目具有两个互补的查看维度：

```Plain Text
任务视角：内容属于什么工作目的
时间视角：项目每天发生了什么变化
```

每日迭代日志可以记录：

- 当天涉及哪些任务；

- 完成了什么；

- 形成了哪些决定；

- 更新了哪些重要文件；

- 当前结果是什么；

- 还有什么遗留问题；

- 下一步是什么。

日志只保存摘要和链接，不复制正式内容。

### 自动维护与用户控制保持平衡

AI 可以直接进行轻量、可逆的维护，例如：

- 更新当前工作笔记；

- 补充用户已经确认的决定；

- 修复相关链接；

- 更新每日迭代日志；

- 将确认后的内容晋升到正式知识。

涉及以下情况时，应先说明影响，并请求用户确认：

- 大规模调整目录；

- 删除或归档重要文件；

- 覆盖正式成果；

- 处理相互冲突的正式文档；

- 改变项目方向；

- 无法判断用户是否真正认可某个结论。

AI 的目标是主动承担管理工作，但不替用户作出关键判断。

## 四、整体运行方式

一次典型的协作过程可以概括为：

```Plain Text
用户自然表达
      ↓
Skill 判断当前状态与信息价值
      ↓
AGENTS.md 提供本项目的具体规则
      ↓
更新对应任务的工作、知识、成果或证据
      ↓
必要时记录版本关系与每日迭代
      ↓
向用户说明发生的实质性文件变化
```

Skill 负责“怎么判断”，`AGENTS.md` 负责“在这个项目中怎么落地”。

## 五、期望效果

### 对用户

用户可以专注于：

- 思考问题；

- 比较方案；

- 表达偏好；

- 作出决定；

- 评审成果。

不需要额外承担大量文件管理工作，也不需要学习复杂的项目管理流程。

### 对 AI

AI 可以更稳定地恢复项目上下文：

- 当前项目目标是什么；

- 哪些结论已经确认；

- 哪些任务仍在推进；

- 当前权威版本在哪里；

- 结论依据哪些来源；

- 最近发生了什么变化；

- 下一步应该继续什么。

这能够减少遗忘、误用旧版本和重复讨论。

### 对项目

项目最终应具备四种能力：

1. **可找到**：能够快速找到相关材料。

2. **可判断**：能够确认哪个版本当前有效。

3. **可追溯**：能够理解结论来源和版本演变。

4. **可继续**：跨对话、跨阶段甚至更换协作者后仍能继续推进。

最终目标不是单纯让文件夹整齐，而是形成一种可持续的人机协作方式：

> 用户通过自然对话推进知识工作，AI 在不增加管理负担的前提下，把对话持续转化为清晰、可信、可追溯、可继续使用的项目知识。
> 
>
